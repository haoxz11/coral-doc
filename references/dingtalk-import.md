# 钉钉文档导入流程

把钉钉文档转成 Markdown 存入 coral 文档库的详细步骤。读取工具优先 dws CLI，兼容钉钉 MCP；图片通过 coral-mcp 上传换长期链接；**幂等与去重依赖本地缓存**（第 2 节，分桶 JSON + skill 自带脚本操作），缓存同时充当存放位置记忆与强制导入的开关（第 3 节），没有缓存记录时回退到纯内容比对的兜底逻辑（第 4.5 节）。

## 1. 读取钉钉文档

**优先 dws CLI**（本地已安装的钉钉命令行，OAuth 已登录）：

```bash
dws doc info --node <ID或URL>    # 元信息：contentType/extension/nodeType，用于类型探测
dws doc read --node <ID或URL>    # 返回 Markdown 格式的文档内容（需文档有下载权限）
```

`--node` 接受文档 ID、`alidocs.dingtalk.com/i/nodes/{id}` URL、`document/edit|preview?dentryKey=` 完整 URL。分享短链（`alidocs.dingtalk.com/i/p/{key}`）无法被 dws 解析，需用户给出完整链接或文档 ID。

**提取稳定标识（缓存主键）**：从 `nodes/{dentryUuid}` 形式的 URL 或直接给出的文档 ID 里取出那个 UUID，即 `nodeId`，作为缓存主键与后续 `--node` 值。

> `document/edit|preview` URL 里的 `dentryKey` **不是**合法独立 nodeId（dws 明确禁止单独提取使用），这种 URL 必须整体传入，缓存主键改从 `dws doc info` 的输出里取 nodeId。拿不到 nodeId 时放弃查缓存，直接走完整导入流程。

**类型探测路由**：仅普通文档（adoc）可 `doc read`。表格（axls）、画板（adraw）、白板（awbd）、多维表（able）等**不支持**——告知用户当前不支持该类型，建议先在钉钉中转为普通文档再导入。

**dws 不可用时**（命令不存在、认证过期且无法续期）：改用会话中已配置的钉钉 MCP，按其实际工具清单完成同等操作（读文档内容、拿元信息）。两者都不可用则告知用户并停止。

## 2. 缓存（幂等与去重的基础）：分桶存储 + 脚本操作

### 2.1 位置与布局

缓存根目录 `~/.coral-doc/`——位于技能仓库与文档库之外，重装技能、重新 clone 技能仓库、切换文档库都不会丢。**分桶存储**，避免单个文件随文档量无限膨胀：

```
~/.coral-doc/
├── libraries/<库地址sha256>/<桶>.json      # 桶 = sha256(nodeId) 前 2 位；桶内 {nodeId: 导入记录}
└── uploads/<实例名>/<桶>.json              # 桶 = 图片sha256 前 2 位；桶内 {图片sha256: 上传记录}
```

每次导入只读写命中的那个小桶文件（万级文档时每桶也只有几十条），单文档记录结构与 v1 相同：`url` / `title` / `target` / `exported_at` / `source_modified`；上传记录：`url` / `name` / `uploaded_at`。

### 2.2 脚本：统一入口，禁止临场写代码

**所有缓存读写都通过 skill 自带脚本**，不要临场写 Python/shell 处理缓存，也不要手改缓存 JSON：

```bash
python3 <skill目录>/scripts/imports_cache.py <子命令>
```

| 子命令 | 参数 | 说明 |
|---|---|---|
| `hash` | `<图片文件>` | 打印文件内容 sha256（去重键，先算哈希再查台账） |
| `lookup` | `<库地址> <nodeId>` | 查文档导入记录；命中打印 JSON，未命中打印 `{}`（退出码 1） |
| `record-import` | `<库地址> <nodeId> <字段=value>…` | 写入/更新文档记录，同键**覆盖式更新**（旧字段保留、同名覆盖） |
| `lookup-upload` | `<实例> <图片sha256>` | 查图片上传记录（去重台账） |
| `record-upload` | `<实例> <图片sha256> <url> <name>` | 登记一次成功上传 |
| `migrate` | 无 | 把旧版单文件 `imports.json` 迁到分桶布局（原文件保留为 `.v1.bak`） |

脚本内置原子写（临时文件 + rename）与损坏自愈：桶文件解析失败时自动备份为 `<桶>.corrupt-<时间戳>` 后按空缓存继续，不会静默丢弃数据。

### 2.3 键的选择

| 键 | 取值 | 为什么 |
|---|---|---|
| 库分组 | 库的**绝对路径**（脚本内转 sha256 目录名） | 「不同库当新文档导出」由此天然成立——同一篇钉钉文档导入到另一个库是另一组记录，互不影响 |
| 文档主键 | 钉钉 `nodeId`（`nodes/{dentryUuid}` 的 UUID） | 稳定、可复现；**不要用 `dentryKey`**（见第 1 节） |
| `target` | 相对**库根**的路径 | 库整体搬移/重命名后记录仍可用 |
| 上传主键 | 图片**内容 sha256** | 与文件名、URL、出现位置无关，同一张图在任何文档里都认定为同一份；跨文档去重天然生效 |
| coral 实例标识 | 库首页 `remote_url` 归一化（去 scheme 与尾斜杠）；拿不到时退化为该库的绝对路径（脚本内转 `lib-<哈希前16位>` 目录） | 上传链接属于某个 coral 实例；**不能跨实例按哈希复用**，否则会得到 404 图片 |

### 2.4 读写规则

- **缓存缺失** → lookup 返回 `{}`，视为空缓存，不报错、不阻塞。
- **写回时机**：图片上传成功**立即** `record-upload`（中途中断也不会重复上传）；文档落盘成功后 `record-import`。
- **覆盖式更新**：同一 nodeId 在同一库下只有一条记录；再次导入与强制导入都是 `record-import` 原地覆盖（更新 `target` / `exported_at` / `source_modified`），不会追加重复条目。
- **失败降级**：脚本执行失败（权限、磁盘）**不阻塞导入**——按"无缓存"继续跑完整流程，并在汇报中说明"缓存未生效"。
- **损坏处理**：由脚本自动完成（备份 + 按空处理）；发现 `.corrupt-*` 文件时在汇报中告知用户。

## 3. 再次导入判定（查 imports 表）

拿到 nodeId 后**用脚本查缓存**：`lookup <库绝对路径> <nodeId>`。**先看使用者是否带了强制意图，再走常规三态分流。**

### 3.1 强制导入（使用者显式要求覆盖）

命中以下任一表达即视为**强制意图**：强制导入、强制覆盖、强制更新、强制重导、强制覆盖缓存、忽略缓存重新导入、force import、force overwrite、force re-import。

强制意图的语义：

- **跳过判定**：不再检查"是否已导入过""源文档是否更新"，直接走完整导入流程。
- **强制更新缓存**：落盘后执行 `record-import` **覆盖**该文档在本库的记录，把 `target`、`exported_at`、`source_modified` 一并更新为本次的值。因为 `imports` 以 nodeId 为键，同一文档在同一库下**天然只有一条记录**，覆盖就是原地更新，不会产生重复条目。
- **不强制重传图片**：图片仍按第 4.4 节的 `uploads` 台账去重——台账命中说明内容确实一致，重传只是浪费。只有使用者另外明确要求"图片全部重传 / 强制刷新图片"时，才忽略台账逐张重传（见 4.4）。
- **位置仍可复用**：强制导入时若使用者未给出新位置，沿用记录里的 `target`；给了新位置则用新位置并更新记录（见 3.3）。

### 3.2 常规三态分流（无强制意图时）

1. **无记录** → 走完整导入流程（第 1、4 节）。图片仍先查 `uploads` 台账，命中就复用。
2. **有记录，但 `target` 指向的文件不存在**（被移动、改名或删除）→ **询问用户**：继续导出到缓存记录的目录，还是重新指定目录？选缓存目录 → 按原位置重新导入；重新指定 → 按新位置导入。**无论哪种，落盘后 `record-import` 都会把 `target` 更新为本次实际落盘路径**——使用者事后挪动了文件位置时，缓存就这样被纠正回来，不会一直指着已不存在的旧路径（也不要在旧位置再导一份造成双份文件）。
3. **有记录，且 `target` 文件存在** → 比源文档最后修改时间：
   - **时间相同** → **跳过导入**，汇报"已导入过 → `<路径>`（导入时间 `<exported_at>`）；需要重新导入请说'强制导入'"。
   - **时间不同** → 源文档已更新，提示"源文档已更新（`<旧时间>` → `<新时间>`）"，让用户选：覆盖更新该文件 / 另存新文件 / 跳过。**选"另存新文件"时，落盘后 `record-import` 把记录的 `target` 更新为新文件**——记录始终指向最新一次导入的落盘位置，旧文件保留但不再是记录位置。
   - **拿不到修改时间**（dws 输出的元信息不保证含最后修改时间字段，`info` 里没有就用 `read` 返回的元信息） → **不要静默跳过**，提示"已导入过（导入时间 `<exported_at>`），但源文档更新时间未知，是否重新导入？"由用户决定。

注：`source_modified` 拿不到时该字段可缺省；下次仍需按"时间未知"分支处理。

### 3.3 位置复用（省掉重新选菜单）

缓存记录同时是一份**存放位置记忆**：

- 记录存在、且使用者**未明确指定位置** → 直接采用记录中的 `target`（相对库根解析为绝对路径），**跳过选一级菜单与候选推荐**，只在落盘前确认里展示路径。
- 使用者**明确指定了位置** → 以使用者的为准，导入成功后把记录的 `target` 更新为新位置（不做"另存一份"）。
- 记录不存在 → 按手写模式的规则选菜单（给 2-3 个候选并附理由）。
- 目标文件已被移动到别的路径、但使用者仍让同一文档导入 → 以使用者给的位置为准并更新记录；不要因为旧路径不存在就报错。

## 4. 图片处理（核心）

钉钉返回的图片是**临时签名 URL，几分钟内过期**——绝不能原样保留在 markdown 里。

### 4.1 发现 coral-mcp

按顺序尝试：

1. **已安装**：当前会话的 MCP 工具中已有 coral 的上传工具（工具描述带 `【coral-mcp】` 前缀，工具名 `upload_file` / `finalize_upload`）——直接使用。
2. **未安装**：读文档库**首页** front matter（根目录分支页回退链 `_index.md` > `index.md` > `readme.md`）中的 `remote_url` 字段——它指向该库对应的 coral 服务实例，MCP 端点为 `{remote_url}/mcp`（JSON-RPC 2.0，POST，`tools/call` 方法）。调用需要鉴权时若拿不到 token，向用户询问。该 `remote_url` 归一化后同时用作缓存里 `uploads` 的分组键。
3. 首页没有 `remote_url` 字段、且 coral-mcp 未安装：向用户询问 coral 服务地址（或让用户安装 coral-mcp），不要猜测。

### 4.2 上传换链接

对每张图片：

1. `upload_file`：参数 `file_name`（含扩展名）、可选 `content_type`。返回 `post_url` 与一组表单字段（含 `object_key`，key 与 Content-Type 被 policy 钉死不可篡改）。
2. 以 `multipart/form-data POST` 把图片字节**直传对象存储**（文件不经过 coral）。**文件字段名必须是 `file` 且放在表单最后**；表单字段不要写到 query 或 header。
3. `finalize_upload`：参数 `object_key` + `file_name`。返回**长期可用的访问链接与现成 markdown 片段**（如 `![名称](链接)`）。

注意事项：

- 单文件大小上限在工具描述中注明（超出会被对象存储直接拒绝）——超限图片告知用户单独处理。
- 非法扩展名、特殊字符文件名可能被拒，重试时改用安全文件名（如 `image-01.png`）。

### 4.3 改写文档引用

用 `finalize_upload` 返回的 markdown 片段（或访问链接）**替换原文中的临时 URL 引用**，逐张对应，不要漏改、错位。

### 4.4 命中台账则不重复上传（主路径）

对每张图片，**先查台账再决定是否上传**：

1. 下载图片到临时目录（这一步无论如何都要做——未命中时要上传它，命中时也要靠内容哈希才能查）。
2. `hash <图片文件>` 算内容 **sha256**（不要用临场命令算）。
3. `lookup-upload <coral 实例> <sha256>` 查台账：
   - **命中** → 直接复用记录里的访问链接，**不调用上传接口**（因此也不需要去旧文档里下载旧图比对、不需要按出现顺序/alt 配对）。
   - **未命中** → 走 4.2 的三步上传，拿到链接后**立即 `record-upload` 回写台账**。

台账命中率只取决于内容是否一致：图片改了就换新哈希、自然重新上传；没改就命中、一次上传都不发。

**强制导入不绕过本台账**（强制的是文档层面的重新导入，不是图片层面的重传）。只有使用者明确要求"图片全部重传 / 强制刷新图片"时，才忽略台账逐张重传，并在摘要中标注重传张数。

### 4.5 兜底：台账无法回答时下载新旧图比对

**触发条件**：目标文件已存在且正文含 `/f/...` 链接（即此前导入过），但**缓存台账无法回答**——缓存目录整个丢失、首次启用缓存、或 `uploads` 分组键（coral 实例）无法确定。此时不能因为台账查不到就把已上传的图片重传一遍，按下面的老办法比对：

1. **提取旧图片**：解析旧文档中所有 `/f/...` 远程链接，连同 alt 文本与出现顺序记录。
2. **配对**：新文档图片（临时签名 URL）与旧图片按**出现顺序 + alt 文本/文件名**配对。
3. **比对是否变更**：下载新旧图片，比对**内容哈希**；比对用的临时文件用完即删。这里回访旧 `/f/...` 链接是幂等判定的必要步骤，发生在落盘之前，不受"落盘后不验证"约束。
4. **处理**：
   - 内容一致 → 沿用旧链接，不调用上传；**并用 `record-upload` 把 `<sha256> → 链接` 回写台账**，下次直接命中。
   - 内容不一致、或新文档中配对不上的新增图片 → 走 4.2 上传换新链接。
   - 旧有新无 → 该引用随正文删除（coral 侧已上传的文件**不删**）。
5. **无法比对时**（旧链接拉取失败、哈希拿不到等）：**默认视为未变更、沿用旧链接**，并在转换摘要中标注"X 张未能比对、默认沿用"；用户明确要求强制刷新时才全部重传。

## 5. 导不出的内容

白板（以及任何导不出图片的内容）：**保留钉钉原文链接**，不做强行转换。可在该位置保留原有的文字说明；如果原文中没有任何说明，保持链接原样即可，并在转换摘要中列出。

## 6. 正文转义还原

钉钉导出的 Markdown 会把部分本应原样的字符写成**十进制 HTML 实体**（dws 与钉钉 MCP 的输出都可能出现）。实测形态：**表格单元格内的代码片段**中 `_` 被写成 `&#95;`，如 `` `ACQUIRER&#95;TRAN&#95;FLOW` ``；coral 的渲染器不解码代码片段内的实体，页面上会原样显示这串转义。

落盘前对全文档做一次实体还原，规则：

- 代码片段（`` `...` ``）内的 `&#95;` 还原为 `_`，直接还原、无需转义（代码片段内 `_` 本就是字面量）；同类数字实体一并还原：`&#42;` → `*`、`&#35;` → `#` 等。
- 两个例外，裸字符会破坏结构时改用 markdown 转义：
  - `&#124;`（`|`）位于**表格单元格**内（含代码片段内）→ 还原为 `\|`，否则会拆列。
  - `&#96;`（反引号）位于**代码片段**内 → 还原会提前终止片段，该处保留实体或改写为代码围栏。
- 普通正文里的反斜杠转义（`\_`、`\+`，如 `chargeback\_order\_info`）是合法 markdown，**保留不动**。
- 还原发生在图片改写之后、落盘之前；还原处数计入转换摘要（第 8 节）。

## 7. front matter 与来源

```yaml
---
title: <钉钉文档标题>
date: <钉钉文档最后修改时间，YYYY-MM-DD HH:MM:SS；拿不到用当天>
---
```

文档**尾部**注明来源（正文最后追加，不是 front matter 字段）：

```markdown
---

> 来源：[钉钉原文 · <文档标题>](<钉钉文档URL>)
```

## 8. 转换摘要（落盘前确认用）

向用户展示的固定格式：

- 目标文件绝对路径（位置复用自缓存记录时标注 `位置复用：<记录中的 target>`）
- 缓存判定（如有查缓存）：`新建导入` / `强制导入（忽略缓存，将覆盖记录）` / `缓存命中但目标文件已不存在（询问后：沿用原位置 / 改为新位置 <路径>）` / `源文档已更新（旧 → 新）` / `源文档更新时间未知`
- 图片：共 N 张，已上传 M 张（失败/超限的列出原因）；区分 **A 张命中台账未重复上传**、**M 张变更/新增已上传**、**X 张走兜底比对沿用旧链接**、**Y 张未能比对默认沿用**（按实际出现的情况列）
- 正文转义还原：N 处（如 `&#95;` → `_`；0 处时不列）
- 导不出的内容：K 处保留钉钉链接（列出是什么，如"白板 ×2"）
- 不支持的元素：清单（如有）

**保真导入是默认行为，不询问是否增强**；可增强点最多在最终汇报中顺带一提，用户主动要求才改写。

确认后写入目标路径。

## 9. 落盘后收尾

- **写入缓存**：文档写入成功后执行 `record-import <库地址> <nodeId> url=<…> title=<…> target=<相对库根路径> source_modified=<源文档修改时间>`（`exported_at` 脚本自动补当天；`source_modified` 拿不到则不传）。缓存写入失败只提示、不回滚文档。
- **不做落盘后验证**：本地文件写入成功即任务完成。不检查站点渲染、不回访图片链接等任何二次确认——本技能只负责生成并落盘文档。
- **清理临时文件**：导入过程中产生的本地临时文件——下载的图片、`doc read` 导出的内容、中间结果（URL 列表、上传结果等）——在落盘完成后**全部删除**，不留遗留。建议每次导入使用独立的临时目录（如 `/tmp/dingtalk-import-<时间戳或ID>`），收尾时整目录删除；目录内若发现非本次导入产生的文件（前次会话遗留），不要复用其结果，直接换新目录。**注意别把 `~/.coral-doc/` 下的缓存桶当临时文件删掉**——那是跨会话的持久缓存。
